# FASE 1 — RFC-DM-001: Domain Model Semantic Amendment

**Status:** Proposed — drafted for Framework Council ratification per Governance Architecture §8-9 (this RFC does not self-ratify; it is the artifact submitted to that process).
**Target document:** Domain Model Architecture v1.0.0
**Resulting version:** Domain Model Architecture v1.1.0 (minor — additive only, see §7)
**Amends:** Findings C1, C2, C3, C4, H1, H3 from the ARB institutional review.

---

## 1. Motivation

Domain Model Architecture v1.0.0 is the semantic layer every future Standard, Policy, Template, Skill, Agent and Workflow will be described against. Two independent ARB review passes identified six defects severe enough to block that dependency chain from starting safely:

- **C1** — `Knowledge` names two incompatible classifiers in the same document (an Output Entity and a Component category), a namespace collision that MOF/UML tooling would reject as ill-formed.
- **C2** — `Context` is declared transitory (§9 of the amended document) while §15 requires it to be reconstructible indefinitely for auditability — a direct contradiction that invalidates every audit performed more than one Execution-lifetime after the fact.
- **C3** — the `derives_from` relation is simultaneously permitted and forbidden for `Knowledge → Knowledge`, contradicted across three sections (§5, §6, §11) of the same document.
- **C4** — the `measures` relation references `Domain` and `Framework` as valid targets, neither of which is a declared entity anywhere in the model — a dangling reference.
- **H1** — `Domain` carries three incompatible meanings across the document set (DDD bounded context, Governance grouping, and the Domain Model document's own self-reference), violating the model's own consistency principle (§19.1).
- **H3** — the `Component:Manifest` cardinality is declared `1:1` in a table that directly contradicts the narrative two paragraphs later, which describes one immutable Manifest per version accumulating over time.

**Cost of non-correction:** every day these defects remain unresolved, they become more expensive to fix, because each subsequent document (Standards, Skills, Agents, Workflows) will cite `Knowledge`, `Context`, `derives_from`, `Domain`, or `Manifest` cardinality as settled vocabulary. Correcting them after even one downstream document exists requires a coordinated multi-document amendment instead of a single one. **The Framework currently has zero instantiated components** — this is the only point in its lifetime where this correction is free.

---

## 2. Scope

### 2.1 What changes
- Terminology: `Knowledge Component` → **`Knowledge Asset`** (C1).
- New specialization: **`Context Snapshot`** as a third specialization of `Artifact`, alongside `Evidence` and `Decision Record` (C2).
- Relationship rule: `derives_from` extended to permit `Knowledge → Knowledge`, under an explicit temporal-monotonicity and cycle-detection constraint (C3).
- Relationship rule: `measures` target set narrowed to `Component`, with forward-compatible extension to `Namespace` once Phase 2 of this same amendment cycle is ratified (C4).
- Terminology: `Domain` reserved exclusively for the DDD bounded-context sense across all Framework documents; Governance's grouping concept renamed **`Governance Area`** (H1).
- Notation fix: `Component:Manifest` cardinality corrected to `1 : 1..*` with explicit UML multiplicity and a derived `current Manifest` view (H3).

### 2.2 What does NOT change
- The fourteen fundamental entities of Domain Model §2 are **not reduced, renamed, or restructured** — `Context Snapshot` is added as a *specialization* of the existing `Artifact` entity, not a new root entity, per §18.2's own rule (specialization over new root entities).
- The five-way classification (Estrutural / Operacional / Conhecimento / Governança / Execução) is unchanged.
- The Component Contract, Kernel lifecycle (`Draft→...→Removed`), and Governance roles/processes are unchanged — this RFC touches only Domain Model Architecture.
- No entity, relationship, or rule is **removed**. Every change below is additive or corrective-of-a-defect, never a narrowing of previously *valid* behavior (see §7 for the formal distinction between "narrowing an error" and "breaking change").

### 2.3 Backward compatibility guarantee
Because zero Components, Executions, Artifacts, Knowledge entries, or Decision Records exist yet under Domain Model v1.0.0, this RFC carries **zero data-migration burden**. Compatibility is therefore demonstrated structurally (§7), not empirically — there is no corpus to break.

## 3. Normative Changes

### 3.1 — C1: Knowledge / Knowledge Asset

**Resolution:** `Knowledge` (Domain Model §2, entity #9) retains its exact original definition: an Output Entity representing derived, validated, reusable understanding. The Component subtype formerly named `Knowledge Component` (§3 hierarchy: Research, Playbook, Knowledge Base Entry) **MUST** be renamed **`Knowledge Asset`**.

A new relationship is introduced to bridge the two, closing the gap that caused the original collision:

> **`codifies`** — `Knowledge Asset → Knowledge`, cardinality **N:N**. A Knowledge Asset codifies one or more Knowledge entries into a durable, citable, governed Component. A Knowledge entry MAY be codified into zero, one, or several Knowledge Assets (e.g., the same derived pattern might appear in both a Playbook and a Research summary).

**Rationale for `codifies` direction and cardinality:** Knowledge (Output Entity) is the raw derived understanding; Knowledge Asset (Component) is the curated, governed, citable form. The direction Asset→Knowledge mirrors how `Decision Record` (Artifact) `references` `Component` — the durable governed artifact points at what it captures, not the reverse. N:N is required because curation legitimately synthesizes multiple Knowledge entries into one Asset (a Playbook consolidating five related derived patterns) and a single Knowledge entry may be cited by multiple Assets.

**Updated hierarchy fragment (Domain Model §3):**
```
├── Component
│   └── Knowledge Asset            [renamed from "Knowledge Component"]
│       ├── Research
│       ├── Playbook
│       └── Knowledge Base Entry
...
├── Output Entity
│   └── Knowledge                  [unchanged — Output Entity, unambiguous now]
```

**Updated glossary entries (Domain Model §20):**
| Term | Corrected definition |
|---|---|
| `Knowledge` | Output Entity: derived, validated, reusable understanding, produced via `derives_from` (Execution \| Research \| Decision \| Knowledge — see §3.3 below). |
| `Knowledge Asset` | *(renamed from Knowledge Component)* Component subtype (Research, Playbook, Knowledge Base Entry) that `codifies` one or more `Knowledge` entries into a governed, versioned, citable artifact of the system. |

**Classification of the original defect:** `[ERRO — modelagem/namespace]`, now resolved by specialization+bridging relationship, consistent with the model's existing pattern (Evidence/Decision Record as specializations of Artifact; now Knowledge Asset formally bridges to Knowledge via a named relation rather than sharing its name).

### 3.2 — C2: Context Snapshot

**Resolution:** `Context` (Domain Model §2, entity #5) is unchanged: it remains the live, mutable, transitory situational state that conditions an Execution while that Execution is in progress. A new entity is introduced:

> **`Context Snapshot`** — a specialization of `Artifact` (alongside `Evidence` and `Decision Record`). An immutable, permanently retained capture of the relevant fields of a `Context` at one specific instant.

**Normative rules:**

1. A Context Snapshot **MUST** be created at the moment an `Execution` transitions from `Initiated` to `Running` (Domain Model §8). An Execution **MUST NOT** enter `Running` without a corresponding Context Snapshot — this is a structural precondition enforced by the same Kernel validation layer that already gates Lifecycle transitions (Kernel Architecture §8), not a best-practice convention.
2. **Responsibility:** the Context Snapshot is captured by the runtime mechanism that initiates the Execution (i.e., it is attributed to the Execution itself via `occurs_within`, not authored by a Role as a separate manual act). This avoids making reliable auditability dependent on a human or Agent remembering to do it.
3. **Immutability:** once captured, a Context Snapshot's content **MUST NOT** be modified. Any change in situational state after capture is, by definition, a different moment and — if relevant — produces a new Context Snapshot tied to a new Execution or an explicitly declared sub-Execution.
4. **Retention:** Context Snapshots are retained under the same permanence rule as all other Artifacts in the Governance/Knowledge classification (Domain Model §4.4-4.5) — indefinite, subject only to formal Archival of the Execution's entire provenance chain, never to silent expiry. This directly resolves C2: `Context` itself may still be discarded when an Execution ends (§9's transitory rule is preserved for the live entity), but the **Snapshot** — the thing audits actually need — persists permanently.
5. **Reference pattern:** `Artifact`, `Evidence`, `Decision Record`, and `Knowledge` (when `derived_from` an `Execution`) **MUST** resolve "under which Context" (Domain Model §15, traceability question #2) by dereferencing the Context Snapshot of their originating Execution — never the live `Context`, which may no longer exist by the time the question is asked.

**Updated relationship:** `occurs_within` (`Execution → Context`) is unchanged. New relationship: **`captured_as`** (`Execution → Context Snapshot`, cardinality **1:1** — every Execution has exactly one Context Snapshot, captured once, at initiation).

**Why specialization of `Artifact`, not a new root entity:** Artifact is already defined as "any tangible, persistent result produced by an Execution or Decision" (Domain Model §2, entity #7) — a Context Snapshot fits that definition exactly (it is *produced by* the Execution's initiation, is tangible/serializable, and persists). Adding it as a third `Artifact` specialization costs zero new root-level concepts, consistent with §18.2's mandate to prefer specialization over parallel entity creation.

**Classification of the original defect:** `[ERRO — contradição interna]` between §9 and §15, now resolved by decomposing "Context" into a live part (unchanged, still transitory) and a persisted part (new, permanent) — the same live/frozen split OpenTelemetry uses for `Resource` attributes and Span emission.

### 3.3 — C3: `derives_from` resolution

**Resolution:** `Knowledge → Knowledge` via `derives_from` is **formally permitted**, resolving the three-way contradiction between Domain Model §5 (table), §6 (Rule 5's wording), and §11 (prose restricting sources to Execution/Research/Decision).

**Updated valid source set for `derives_from`:**
> `Knowledge derives_from {Execution, Research, Decision, Knowledge}`

**Mandatory constraints (both required, no exceptions):**

1. **Temporal monotonicity.** For any edge `K2 derives_from K1` where `K1` is itself a `Knowledge` entity, `K1.established_at` **MUST** be strictly earlier than `K2.established_at`. This applies transitively across the whole `derives_from` graph, not just direct edges.
2. **Cycle prohibition.** The `derives_from` graph over `{Execution, Research, Decision, Knowledge}` **MUST** be acyclic. This reuses, without modification, the exact cycle-detection mechanism Kernel Architecture §7 already mandates for the Component `dependencies` graph — no new validation machinery is introduced, only a second graph it is applied to.

Together, rules 1 and 2 make the pathological case impossible by construction: a `Decision` cannot be `informed_by` a `Knowledge` that in turn `derives_from` that same `Decision`, because rule 1 alone already forbids `K1` from being newer than or equal to what it feeds.

**Concrete case this now legalizes** (from the ARB review's example): a Steward consolidating three language-specific SQL-injection Knowledge entries into one general-pattern Knowledge entry now has an explicit, valid mechanism: the general entry `derives_from` all three specific entries, each strictly older, non-cyclically.

**Updated Domain Model §5 table row:**
| Relacionamento | De | Para | Natureza |
|---|---|---|---|
| `derives_from` | Knowledge | Execution \| Research \| Decision \| **Knowledge** | N:N, **acyclic, temporally monotonic** |

**Classification of the original defect:** `[ERRO — contradição interna]`, now resolved in favor of the more permissive, better-aligned reading (consistent with W3C PROV-O's `wasDerivedFrom`, which already supports Entity→Entity derivation chains).

### 3.4 — C4: `Framework` / `Domain` invalid references

**Resolution — chosen approach: replace, not formalize `Framework`; resolve `Domain` via H1's terminology fix; extend `measures` forward to a Phase-2 concept.**

1. **`Framework` as a `measures` target is removed.** No entity named `Framework` is introduced. Rationale: introducing a `Framework` singleton entity solely to patch one dangling reference would be exactly the kind of ad hoc, non-derived entity Domain Model §18.1/§19.2 warns against. The concept "a metric about the whole system" does not need its own entity — it needs a **scope**, and Namespace (Phase 2 of this document, §8) already provides exactly that: the root Namespace is, by construction, the whole system.
2. **`Domain` as a `measures` target is removed** as an immediate consequence of H1 (§3.5 below) — until this RFC, "Domain" in this position was already ambiguous among three meanings; none of them was ever a declared entity, so no valid usage is lost.
3. **Forward extension:** `measures` targets are updated to `{Component, Namespace}`. `Namespace` is formalized in Phase 2 of this same amendment cycle (Identity & Namespace Architecture, below) — by the time this RFC is read in full, the forward reference is already closed, not left dangling. A metric formerly imagined as "Framework-level" is now correctly expressed as "a Metric scoped to the root Namespace."

**Updated Domain Model §5 table row:**
| Relacionamento | De | Para | Natureza |
|---|---|---|---|
| `measures` | Metric | Component \| **Namespace** | N:1 |

**Why this is not a breaking change:** `Domain` and `Framework` were never resolvable references to begin with (that is the literal definition of C4) — no conformant system could have depended on them, because no conformant system could have implemented them. Removing an option that could never have worked is a defect fix, not a capability removal. See §7 for the formal argument.

**Classification of the original defect:** `[ERRO — referência a tipo não declarado]`, resolved by scope-substitution rather than ad hoc entity creation.

### 3.5 — H1: "Domain" terminology standardization

**Resolution:** `Domain` is reserved, across every document in the Framework, exclusively for its Domain-Driven Design sense: **a bounded business/product context to which Components may be scoped** (e.g., "billing", "identity", "payments-fraud"). This is now a legitimate, lightweight concept referenced by Namespace (Phase 2, §3) but is **not** independently formalized as a full entity in this RFC — it remains, for now, a scoping label carried in Component `metadata` (Kernel Architecture §2.14), consistent with the original design; only its *name* is disambiguated here, not its structural depth (that remains appropriately deferred to a future Organization/Tenancy document per the roadmap, avoiding scope creep in this RFC).

**Consequential terminology change:** the Governance grouping previously called "Domain" / "Domain Steward" (Governance Architecture §2, §4) is renamed **`Governance Area`** / **`Governance Area Steward`**. This is an **editorial, non-structural** amendment — no process, authority, or responsibility defined in Governance Architecture changes; only the label does. Per Governance Architecture's own hierarchy (§8), a purely editorial rename does not require the same RFC weight as a structural change to that document; it is recorded here as a **consequential action** of this RFC and takes effect the same day this RFC is ratified. `Domain Steward` is retained as a **deprecated alias** for one full documentation cycle (Governance Architecture Deprecation lifecycle, §6) purely for human continuity — no machine reference existed to migrate, since no Governance Area instances exist yet either.

**Classification of the original defect:** `[ERRO — ambiguidade cross-document]`, resolved by exclusive reservation of the term plus a renamed, non-structural consequential edit elsewhere.

### 3.6 — H3: Component:Manifest cardinality

**Resolution:** the Domain Model §7 cardinality table entry is corrected from the ambiguous `1:1` to the UML-correct multiplicity:

> **`Component "1" —— "1..*" Manifest`**

**Explanation:**
- Every `Component` **MUST** have at least one `Manifest` (its first version) and **MAY** accumulate arbitrarily many over its lifetime — each immutable once published, per Kernel Architecture §8, none ever deleted (only superseded).
- A derived, non-stored, queryable view is introduced for convenience, using UML dependency notation (not a persisted relationship, computed on demand):

> **`Component ┄┄▷ Manifest : current`** (multiplicity **0..1** — zero only in the impossible-in-practice case of a Component with no version at all, which cannot occur post-`Draft`; exactly one otherwise, defined as the Manifest of the highest version among those whose Lifecycle state is `Active`).

**Justification for keeping both notations:** collapsing to a single relationship would re-introduce exactly the ambiguity being fixed — "1:1" was wrong because it silently meant *two different things* (per-version vs. lifetime). Making both explicit (the full historical multiplicity, and the derived "current" convenience view) removes that silent conflation without discarding either legitimate meaning.

**Classification of the original defect:** `[ERRO — inconsistência entre tabela e texto]`, resolved by correct UML multiplicity plus an explicitly-labeled derived view.

## 6. Migration Notes

Because Domain Model v1.0.0 has **zero instantiated entities** (no Components, Executions, Artifacts, Knowledge, or Decision Records exist under it), migration consists entirely of **document text replacement**, with no data backfill:

1. Replace `Knowledge Component` with `Knowledge Asset` everywhere it appears (§2, §3, §16, §20).
2. Insert `Context Snapshot` as a third `Artifact` specialization (§2, §3, §16, §17).
3. Update `derives_from` source set and constraints (§5, §6, §11).
4. Update `measures` target set (§5).
5. Replace ambiguous `Domain` usages per H1's disambiguation; propagate the `Governance Area` rename into Governance Architecture as a non-structural editorial pass.
6. Correct `Component:Manifest` cardinality notation (§7).

No implementation exists yet to be "migrated" in the runtime sense — this section exists to satisfy the Governance Architecture's Breaking Change process (§10) formally, even though its substantive trigger condition (existing Consumers) is vacuously satisfied.

## 7. Backward Compatibility

**Formal claim: this RFC introduces zero breaking changes.**

| Change | Type | Why it is not breaking |
|---|---|---|
| `Knowledge Component` → `Knowledge Asset` | Rename | No instance data exists under the old name; `Knowledge Component` is retained as a deprecated documentation-only alias for one cycle. |
| `Context Snapshot` added | Addition | New specialization of an existing entity (`Artifact`); adds a relationship (`captured_as`), removes nothing. |
| `derives_from` extended to include `Knowledge` | Addition (relaxation) | Previously prohibited-by-contradiction; now explicitly permitted under constraint. Widening a validation rule cannot break a conformant producer, only enable previously-rejected valid cases. |
| `measures` narrowed to `{Component, Namespace}` | Removal of invalid options | `Domain` and `Framework` were never resolvable — no conformant consumer could have depended on them (a reference to an undeclared type cannot have a valid conformant implementation by definition). Removing a non-functional option is a defect fix, not a capability regression. |
| `Domain` reserved to DDD sense; `Governance Area` renamed | Terminology | Purely editorial; no process, authority, or entity structure changes in Governance Architecture. |
| `Component:Manifest` cardinality corrected | Notation fix | The *actual* rule (one immutable Manifest per version, accumulating — Kernel Architecture §8) was already correctly stated in prose; only the summary table was wrong. No system built correctly per the prose is affected; a system built per the incorrect table was already non-conformant with the Kernel and needed this fix regardless. |

**Conclusion:** every change is additive, corrective of a defect with no valid prior behavior, or purely editorial. Per Governance Architecture §10, none of the six changes meets the definition of a Breaking Change (an alteration that "invalidates an expectation of compatibility already assumed by Consumers" — there are, by construction, no Consumers yet).
